## Proposed Danger Zone interface

Keep the existing Super Admin shell, page title and general settings. Add a dedicated full-width **Academic Term Management** section with a small **Danger Zone** label, a restrained red rule, square geometry, compact definition rows and no colored card gallery. Reserve the strongest danger treatment for the final activation action.

1. Show the fetched current year/semester, status, and last activation time. Loading, failed, missing-schema, no-active and multiple-active states are explicit. A failed read never displays cached values as confirmed current state.
2. Select a configured draft matching the immediate next semester. Do not preselect or offer a skipped/closed term. Draft creation retains its existing authorized server path and is visibly separate from activation. Bootstrap is a separate future flow, not normal semester transition.
3. Request an authoritative impact preview. Show source → target, generated/expiry times, population definitions, verification counts, program conflicts, affected elections, notification recipients and blocking reasons. Unknown counts are “Unavailable,” never zero. Permit retry without mutation.
4. Review preserved records and consequences. Require an unchecked acknowledgement and exact typed `ACTIVATE <semester> AY <academic year>` confirmation. Clear both after target changes, refresh, term changes, expired preview or revised impact. Use an inline review to avoid introducing a new portal modal contract; move focus to the review heading and announce feedback.
5. Enable activation only after a fresh trusted preview, no blockers, current authorization, and explicit confirmation. Disable all duplicate submissions while pending. On conflict, clear the review and require a fresh preview. A timeout is an unknown outcome: look up the durable operation receipt before retrying; never blindly activate another term.
6. On verified commit, show actual resulting term, operation/audit reference, counts and notification delivery status. A notification retry is not another activation. On failure, show a safe actionable error without claiming that nothing changed unless rollback/receipt lookup proves it.
7. Link to existing Audit Logs. Display transition history only through authorized audit readers, with source, target, verified actor, timestamp, request ID and result. Term status/timestamp rows are configuration history, not a substitute for actor-attributed audit history.

**Local implementation boundary:** render current term and existing draft data through the existing term read. Build the selection, impact explanation and explicit confirmation rehearsal. All affected-count values remain unavailable because no trusted preview exists. “Activate academic term” stays disabled with a visible reason and has no mutation handler. A local review acknowledgement is explicitly temporary and is not an audit event or activation success. Keep existing draft creation; do not add any write contract. No student/profile, eligibility, backend or SQL changes in this pass.

## Term-transition impact analysis

Compute preview aggregates in one consistent server snapshot; do not fetch student rosters into the browser to calculate counts. Use distinct identities to avoid multiplying counts across memberships. Counts must include their precise cohort and calculation time:

- Total persistent accounts, split by existing `pending`, `active`, `disabled` values.
- Distinct enrolled identities in the source term; distinct verified/enrolled identities already in the target term.
- Active source-enrolled accounts lacking verified target enrollment: the primary cohort newly requiring verification. Report all active identities lacking target evidence separately; those two populations are not interchangeable.
- Target enrollment rows with non-enrolled statuses or conflicting/ambiguous identity and program evidence; blocked/skipped sync rows.
- Intended program and institution participation, unresolved program mappings and incompatible current program memberships; manual carry counts separately.
- Election counts by term and phase, including live campaign/voting and future scheduled elections belonging to the term being closed. Block normal activation when this would strand an ongoing/scheduled election; resolve through existing authorized lifecycle processes, never adjust dates, reopen schedules or relabel election terms automatically.
- Student notification recipient count and delivery readiness; historical records preserved, not described as “reset.”

Activation changes operating term and establishes only evidence-backed target participation. It does not import a roster, verify all students, advance year levels, change central statuses, change passwords/sessions/navigation, rewrite past enrollment, modify old membership rows, delete candidacy/officer/vote/receipt records, or mutate election schedules/frozen electorates. Old-term memberships and WITSG participation remain historical; current-term restricted participation still requires current evidence.

## WITSG preservation and program-shift reconciliation

Treat WITSG as `membership_scope='institution'` regardless of its visible organization type or any student's program. A verified BSIT → BHM example means the same persistent `students.id`, a new verified enrollment snapshot, the mapped new program organization(s), and institution-wide WITSG. The repository's guarded historical catalog uses **BSHM**, so do not assume “BHM” is a verified alias or auto-create a mapping during transition. Resolve through trusted catalog/approved identity review.

1. Match authoritative import/verification evidence to the existing student identity using existing normalization and conflict review. Never create a second identity to represent a shift or match by mutable profile program.
2. Compare incoming verified program to term enrollment/history. Require authorized approval for shifted rows and invalidate approval if the evidence fingerprint changes. Persist the verified year level as provided; never increment it automatically.
3. Reuse the guarded enrollment/finalizer and membership sync paths. Hold a stable active-term row and the established student/term lock; verify lock ordering with term activation and imports in isolated database tests.
4. Remove only incompatible **current-term program-specific participation**, using existing removal metadata; establish mapped new current-term program participation atomically. Keep previous-term PSITS untouched. Retain all structural links that history depends on.
5. Do not remove institution/manual participation as a side effect of program reconciliation. Preserve WITSG's institution eligibility, subject to verified enrollment and established explicit-removal/restoration policy. Audit and resolve the import-vs-individual restoration asymmetry before claiming parity.
6. Prevent incompatible current program memberships, not every instance of more than one organization. Existing mappings may legitimately cover multiple organizations for one program. Legacy incompatible non-system rows or ambiguous coverage are blockers for explicit review; never delete them or weaken admission guards.
7. Keep elections, participation history, candidacies, votes, receipts and officer records attached to the same identity. Historical access remains under existing authorization.

## Student profile proposal

Use two sections: **Current Organizations** (canonical active-term memberships with verified enrollment context) and **Previous Organizations** (authorized term history with academic year/semester and prior participation status). WITSG can legitimately appear in both sections for different terms. Historical `status='active'` means participation during that historical term, not current eligibility. Removed current-term rows need an accurate ended/removed explanation rather than being labeled a previous semester.

Keep history read-only, scoped to the caller's JWT-derived identity and existing Board/Super Admin authorization. Paginate and minimize fields. Never infer “none” from a failed history read. No frontend historical query or actual profile change is included because the inspected contracts expose current memberships only. An approved server-reader extension is required first.

## Security and regression test plan

**This local pass:** build; targeted lint; existing System Settings tests; semantic tests for immediate-next selection, missing/multiple/invalid active terms, stale local review reset and a permanently disconnected activation action. Browser fixtures intercept all external requests, use synthetic identities, and check 1280px desktop, 768px tablet and 390px mobile, title hierarchy, square geometry, keyboard labels/focus and overflow. Exercise loading/error/retry/no-draft/confirmation states. Verify no term activation or student-table requests leave the page. Existing general settings save and draft creation contracts are preserved.

**Before backend approval/deployment:** isolated Postgres tests with installed-contract parity, not production fixtures that mutate real rows:

- Missing/expired JWT, disabled/Board/unlinked/ambiguous admin, forged actor, unexpected fields and direct anon/authenticated RPC/table writes fail closed; secrets never appear in responses.
- Source→next sequence, year rollover, separate bootstrap and recovery, unique active term, two admins/tabs, competing successive targets, stale/expired/mutated previews, duplicate request IDs, lost responses and idempotent receipt recovery.
- Concurrent import, verification, program-mapping change, membership correction and transition: consistent lock order, no deadlock-driven partial result, stale preview rejected, no wrong-term writes.
- Inject membership sync, audit and notification-intent failures: entire transition rolls back. Delivery failure after commit leaves a committed transition with retryable delivery, not a second activation.
- Verified/unverified/withdrawn/not-in-masterlist students retain normal login/navigation; every restricted voting and candidacy entry point rejects absent current-term enrollment on the server. Direct API and stale-browser attempts cannot bypass it.
- BSIT→verified BSHM/BHM-approved-alias shift keeps same identity/WITSG, ends only incompatible current program rows, preserves manual membership, handles explicit removals, detects legacy conflicting sources, and changes no previous-term rows.
- Incremental vs full-roster confirmation, duplicate/ambiguous identities, shifted-row approval and fingerprint changes; no automatic year advancement or central account disablement.
- Historical own-profile access and cross-student/Board boundaries, unavailable-history feedback and pagination; current and historical WITSG shown accurately.
- Preserve schedules and candidacies, officer records, duplicate-vote races, abstain, historical receipts/results, JWT identity, Ballot V1 canonicalization, vote/ballot hashes and anchoring retry behavior. Compare immutable historical rows/checksums before and after isolated transitions.

## Rollout and rollback

Local UI changes are confined to `SystemSettings.jsx`, a term Danger Zone component, its scoped CSS, a pure presentation helper, tests and this plan. Preserve pre-existing modifications; retain exact before-images of edited files under a task-specific `.tmp` folder. Review only the task delta. Remove/reverse only this patch to roll back local work; never reset or restore the whole worktree. Draft creation and general settings persistence keep their existing boundaries. Activation from this proposed UI is deliberately unavailable.

Before any later rollout, obtain explicit approval for the exact backend/schema/eligibility work, compare deployed contracts through read-only inspection, capture approved function/ACL/constraint before-images, validate in isolation, and prepare forward + rollback proposals without rewriting migration history. Release trusted contracts before enabling the UI and enable only after a verified preview/audit/notification test. Do not use `db push --include-all` or migration repair.

If an approved activation transaction fails, it rolls back entirely. If the response is lost, recover its receipt before deciding whether it failed. After a committed transition, immediately disable further activation if a defect appears, preserve new-term imports/evidence/audits and investigate read-only. **Do not reactivate a closed term, delete notifications/audits, reverse memberships or overwrite new enrollment as a generic rollback.** A committed term/data correction requires its own impact review and explicit authorization; the normal next-term RPC cannot reverse it. Notification delivery can be retried independently. Never reopen/retime elections or undo votes as rollback.
